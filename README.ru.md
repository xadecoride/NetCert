# NetCert

Локальный проект для практики по сертификационным направлениям Cisco и Juniper: Go API, интерфейс Next.js и банки вопросов в PostgreSQL. Основной сценарий — регистрация, выбор экзамена, ответы на вопросы, разбор пояснений и сохранение истории попыток.

NetCert — независимый учебный проект, не официальный продукт Cisco или Juniper. Названия в каталоге и сгенерированные вопросы не подтверждают соответствие актуальным официальным программам экзаменов, полное покрытие сертификаций или готовность к сдаче.

## Реализованный объём

| Область | Что присутствует в исходном коде |
|---|---|
| Учётные записи | Регистрация, вход, bcrypt-хеширование паролей, JWT access tokens, API профиля и настроек |
| Экзаменационная практика | Каталог направлений и экзаменов, получение вопросов, создание попытки, отправка ответов, завершение и история |
| Форматы вопросов | Один ответ, несколько ответов и заполнение пропуска; текстовые simlet-сценарии оцениваются как single choice |
| Обучение | Учебные страницы, отметки о прохождении материалов и API содержимого quick labs |
| Контент | Миграции PostgreSQL и Python-генераторы банков вопросов |
| Экспериментальные лаборатории | API лабораторий и сессий, WebSocket-терминалы, топологии Containerlab и Python-проверки; нужна отдельная инфраструктура |

Наличие типов drag-and-drop или topology в модели не означает готового интерактивного интерфейса и оценивания. Живые лаборатории не входят в стандартный запуск Compose.

## Архитектура

```text
Браузер / Next.js UI
  -> Go HTTP API (Chi + JWT middleware)
  -> use cases
  -> PostgreSQL repositories (pgx)
  -> пользователи, вопросы, ответы, попытки и учебный прогресс

Python-генераторы -> SQL-миграции goose -> банки вопросов PostgreSQL

Отдельный экспериментальный контур:
Go lab endpoints / WebSockets -> Containerlab / Docker -> узлы и проверки лабораторий
```

| Слой | Стек |
|---|---|
| Backend | Go 1.25.7, Chi v5, pgx/v5, goose v3, JWT, bcrypt, Gorilla WebSocket |
| Frontend | Next.js 15, React 19, TypeScript, Tailwind CSS 4; xterm и React Flow для лабораторных экранов |
| База данных | PostgreSQL 16 |
| Подготовка контента | Python-скрипты, генерирующие SQL-миграции |
| Среда разработки | Docker Compose; Redis 7 объявлен, но его runtime-использование в проверенных путях backend не найдено |
| Экспериментальные лаборатории | Containerlab, Docker-in-Docker, Juniper cRPD, Alpine sandbox, FRRouting и Python-проверки |

## Быстрый старт: локальная практика

Нужны Git, Docker Engine и Docker Compose v2.

```bash
git clone https://github.com/xadecoride/NetCert.git
cd NetCert
cp .env.example .env
# Проверьте .env: учётные данные БД, JWT_SECRET и порты хоста.
docker compose up --build -d
docker compose ps
```

Адреса по умолчанию:

| Сервис | Адрес |
|---|---|
| UI | http://localhost:3000 |
| API health | http://localhost:8080/health |

Compose описывает PostgreSQL, Redis, одноразовый сервис миграций, backend и frontend. Backend при старте также запускает встроенные миграции goose. Настройки по умолчанию предназначены для локальной разработки: замените пароли и JWT-секрет перед доступом извне доверенной лаборатории, ограничьте опубликованные порты БД и Redis.

```bash
docker compose logs -f migrations backend frontend
docker compose down
```

`docker compose down` останавливает стек без удаления именованных томов. Не удаляйте тома, если нужно сохранить пользователей и историю попыток.

Команды основаны на конфигурации репозитория; полная контейнерная сборка и запуск при этом обновлении документации не выполнялись.

### Разработка без Docker

Нужны Go **1.25.7 или новее**, Node.js 22+, npm и локальный PostgreSQL 16. Скопируйте `backend/.env.example` в `backend/.env`, локально настройте DSN базы и JWT-секрет. База приложения должна существовать до запуска backend.

В разных терминалах, из корня репозитория:

```bash
cd backend
go run ./cmd/server/
```

```bash
cd frontend
npm ci
npm run dev
```

Python нужен для генерации контента, не для работы Go API. Redis входит в предоставленный Compose, но это само по себе не подтверждает действующую интеграцию кеша или очереди.

## Работа с приложением

1. Откройте UI и зарегистрируйтесь на `/auth/register` либо войдите на `/auth/login`.
2. Выберите направление и экзамен на `/exams`, начните попытку.
3. Отправляйте ответы и завершите попытку для подсчёта результата.
4. Просмотрите результат, пояснения и историю; на учебных страницах отмечайте прохождение материалов.
5. Интерактивные лаборатории рассматривайте как отдельную среду: наличие терминала в UI не означает доступного sandbox или сетевого узла.

API использует префикс `/api/v1`; авторизованные HTTP-запросы передают access token в `Authorization: Bearer …`. Маршруты определены в [router.go](backend/internal/delivery/http/router.go).

| Группа | Примеры |
|---|---|
| Авторизация | `POST /api/v1/auth/register`, `POST /api/v1/auth/login` |
| Каталог | `GET /api/v1/tracks`, `GET /api/v1/tracks/{slug}/exams` |
| Попытки | `POST /api/v1/attempts`, `POST /api/v1/attempts/{attemptId}/answers`, `POST /api/v1/attempts/{attemptId}/complete` |
| История | `GET /api/v1/attempts/history` |
| Учебный прогресс | `GET /api/v1/study/progress`, `POST /api/v1/study/progress/toggle` |
| Лаборатории | `/api/v1/labs`, `/api/v1/quick-labs` и авторизованные `/ws/...` endpoints |

## Генерация банков вопросов

Текущая точка входа генератора поддерживает четыре цели:

| Цель | Файл в `backend/migrations/` |
|---|---|
| `ccna` | `077_ccna_quality_questions.sql` |
| `jncia-junos` | `078_jncia_junos_quality_questions.sql` |
| `jncip-ent` | `079_jncip_ent_quality_questions.sql` |
| `jncip-sp` | `080_jncip_sp_quality_questions.sql` |

```bash
# Одна цель; без аргумента генерируются все четыре.
python3 scripts/generate_quality_questions.py ccna
git diff -- backend/migrations
```

**До проверки результата используйте только отдельную тестовую копию и одноразовую БД.** Генератор перезаписывает миграции `077`–`080`, а полученный SQL удаляет существующие вопросы соответствующих экзаменов перед вставкой новых. Изменение уже применённой goose-миграции не приводит к её автоматическому повторному применению. Это обслуживание контента, не безопасная команда обновления работающей базы.

## Экспериментальный лабораторный контур

[infra/docker-compose.staging.yml](infra/docker-compose.staging.yml) описывает отдельную staging-среду с привилегированным DinD, Alpine sandbox и FRRouting. Топологии и проверки находятся в [backend/labs](backend/labs); оркестрация и WebSocket-обработчики — в Go backend.

Этот контур нельзя считать готовым запуском лабораторий одной командой:

- Dockerfile backend не устанавливает бинарник `containerlab`, хотя оркестрация его ожидает.
- Staging backend работает от непривилегированного пользователя с подключённым Docker socket хоста; права доступа и изоляцию нужно проверить отдельно.
- Вендорские образы, доступ к устройствам, маршрутизация терминалов и проверка заданий требуют настройки среды.
- Staging-сервис миграций выполняет SQL через `psql`; это не тот же процесс миграций, что в стандартном Compose.

Используйте изолированный лабораторный хост. Не публикуйте Docker/DinD API, терминалы и тестовые учётные данные в интернете.

## Структура репозитория

```text
backend/cmd/server/              Точка входа API и сборка зависимостей
backend/internal/delivery/       HTTP- и WebSocket-обработчики
backend/internal/usecase/        Авторизация, экзамены, обучение и лаборатории
backend/internal/repository/     Работа с PostgreSQL
backend/migrations/              Миграции схемы и банков вопросов
backend/labs/                    Экспериментальные топологии и проверки
frontend/                        Страницы Next.js, компоненты и API-клиент
scripts/                         Генераторы контента и служебные утилиты
infra/                           Dockerfile и staging/lab-конфигурация
```

## Проверка и ограничения

Локальная проверка **18 ноября 2026 года**, исходная ревизия `f686d5c` до изменения документации:

```bash
cd backend
go test ./internal/...
```

Команда завершается **ошибкой**: `internal/usecase/auth_usecase_test.go:83` обращается к полю `AuthResponse.RefreshToken`, которого нет в текущей модели. Пакеты тестов HTTP-обработчиков и PostgreSQL-репозиториев в этом запуске прошли. Это не успешный полный набор backend-тестов, не проверка живых лабораторий и не приёмка всего приложения.

Дополнительные границы, обнаруженные при чтении исходного кода:

- Авторизация использует access tokens; устаревший тест не подтверждает наличие refresh-token-механизма.
- Pause/resume лаборатории меняет статус записи в БД, но не реализует снимки или приостановку устройств.
- WebSocket SSH proxy передаёт идентификаторы сессии и пользователя в порядке, отличающемся от сигнатуры use case; нужны исправление и проверки владения сессией.
- Некоторые форматы экзамена имеют объявления в модели или статическое содержимое, но не полный интерфейс и оценивание.
- Правильность вопросов и соответствие актуальным официальным программам требуют отдельной проверки.
- Тестовые секреты, опубликованные порты и привилегированные лабораторные сервисы нужно защитить до совместного развёртывания.
